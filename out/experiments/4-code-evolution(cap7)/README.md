# 경기 보상 기반 진화 실험 — 2026-09-28 KST

**Models.** Primary: **cap7** (the incumbent every candidate had to beat). Also: v3 (baseline), v2 and the official Lv2 (opponents), and the candidates `g1-*`, `g2-*` and `independent` (sources kept in `candidates/`).

## 결론

두 세대에서 실제 후보 소스 7개를 생성·실행했다. 공식 로컬 엔진의 선발 216경기, 미사용 확인 350경기, 합계 **566경기**를 `games.jsonl`에 기록했다. 추가 스모크·실제 프로세스·실패 리플레이·제출 검사 29경기를 포함한 실제 실행은 **595경기**다. 승 1·무 0.5·패 0 보상이며 기록된 선발·최종 경기의 몰수 0건이다. 선발·최종 경기 실행 시간 합계는 534.1초, 중앙값은 0.977초다. 사전 예산은 [PLAN.md](PLAN.md)의 600경기·900초였고 예산 안에 끝났다.

**최고 유지 정책은 기존 cap7-low다.** 최종 미사용 시드의 Y 56경기에서 v3 36승, cap7-low 42승, 1세대 깃발병 생존 후보 42승이었다. 새 후보는 사전 고정한 incumbent 대비 +3승 승격 기준에 못 미쳤다. K 진영 진단에서는 생존 후보가 9/14승, cap7-low가 5/14승이었으나 대회 우선 진영은 Y다. 실제 상대 팀 승률이나 공식 서버 성능으로 해석하지 않는다.

집결형의 선발 실패는 시드 400·v2 상대 리플레이에서 다시 확인했다. 같은 상태였던 **13턴**에 집결형은 `(1,7)`의 전투병 3명을 오른쪽으로 보내고 cap7은 아래쪽으로 보냈다. 20턴 건물 Y:K는 집결형 4:11, cap7 7:7이었다. 집결형은 104턴 0:15 즉시 패배, cap7은 160턴 9:6 점수 승리였다. 한 명령만을 인과 원인으로 단정할 수 없지만, 중앙 한 곳으로 몰린 전투병이 주변 점령 손실을 막지 못한 사례다. 건물 주변 위협을 우선하는 `defend_w` 구조도 2세대에서 두 계보로 시험했으나 각각 9/24, 5/24승에 그쳤다. 원본은 `failures/g1-focus_w-vs-v2-seed400.json`과 `failures/cap7-vs-v2-seed400.json`이다.

최종 평가 대상에 2세대 최고만 남겨 1세대 강자를 누락한 계보 보존 오류를 발견했다. 기준선 64경기를 기록한 시점에 실행을 중단하고, 최종 대상을 **v3·cap7·독립 정책·1세대 최고·2세대 최고**로 고쳤다. 재실행은 기록된 경기를 건너뛰었고, 총 566개의 중복 없는 경기로 종료했다. `test_evolve.py`가 후보 소스 일치, 경기 키 중복, 시드 분리, 몰수, 판정 재집계를 확인한다.

각 정책은 동일한 7상대 × 8시드 = 56개의 Y 경기를 치렀고, K는 같은 상대의 시드 500–501 14경기만 대칭성 진단으로 치렀다.

## 리플레이 실패 사례와 실행 검사

시드 502의 빠른 공격형 K 상대에서 두 정책의 첫 Y 명령 차이는 **12턴**이었다. cap7은 `(3,7)`의 깃발병을 오른쪽, `g1-safe_goal`은 아래쪽으로 보냈다. 20턴 생존 후보의 건물은 Y:K 8:8, cap7은 7:9였으나 종료 시 생존 후보 7:9·점수 14:21 패, cap7은 7:6·14:11 승이었다. 이 한 이동만으로 패배 원인을 단정하지 않는다. 원본은 `failures/g1-safe_goal-vs-fast-attack-seed502.json` 및 `failures/cap7-vs-fast-attack-seed502.json`에 있다. 반대 사례인 생존 후보의 느린 수비형 시드 501 승리 리플레이도 `failures/`에 보존했다.

최고 유지 정책 cap7을 **별도 프로세스**로 시드 600–604에서 v3 K와 겨룬 결과 몰수·프로토콜 오류는 0건이고 0승·5패였다. 같은 시드의 인프로세스 결과도 cap7 0/5, v3 기준선 3/5로 일치한다. 앞의 56경기 우세를 과장하지 않기 위한 반례이며, 이 사후 진단 시드로 후보를 새로 만들거나 최종 평가 조건을 변경하지 않았다. `selected-subprocess-check.json`, `process-seed-context.json`에 원본이 있다. 프로세스 기록 최대 턴 시간 634.76ms에는 첫 턴의 별도 3초 제한이 포함되며 일반 턴 시간 초과 몰수는 없었다.

검토 ZIP `out/v0-unsubmitted/cap7-codex/cap7.zip`은 공식 Windows 패키저로 만든 이전 검증본이며 이번에 다시 확인했다. `main.py`는 최종 cap7 소스와 바이트 일치, 항목 6개 모두 mode `100666`이다. WSL 공식 `run_tests.py --zip` 결과 `ok: true`, issues·warnings 없음, 16턴 즉시승, 턴당 stdout 최대 331바이트·20줄, 한 줄 최대 87바이트, stderr 0. 검사 JSON은 [`local-zip-check.json`](../../v0-unsubmitted/cap7-codex/local-zip-check.json)이다(이전 이름 `selected-zip-check.json`). WSL Python 3.14.4와 서버 Python 3.12.14가 다르며 **이번 ZIP의 공식 서버 검사·온라인 제출·모의 전투는 수행하지 않았다.** 평가용 코드 선택도 변경하지 않았다.

## 재실행과 LLM 사용

WSL의 저장소 루트에서 `python3 "out/experiments/4-code-evolution(cap7)/evolve.py"`를 실행한다. 중단하면 같은 명령으로 이미 기록된 경기 키를 건너뛰며 이어서 진행한다. 결과 검사는 `python "out/experiments/4-code-evolution(cap7)/test_evolve.py"`, 실제 프로세스 확인은 `python3 "out/experiments/4-code-evolution(cap7)/check_selected.py"`, 대표 경기 재생은 `python3 "out/experiments/4-code-evolution(cap7)/inspect_failure.py" g1-safe_goal fast-attack 502`다. 각 후보는 `out/experiments/4-code-evolution(cap7)/candidates/`에 고정된 소스로 남아 있다.

폴더 정리 후 확인: `evolve.py`는 새 위치에서 다시 실행하면 기록된 566경기를 모두 건너뛰고 새 경기를 0판 치렀으며 `games.jsonl`은 바이트 그대로였다. `test_evolve.py`도 통과한다. 다만 재실행은 `generation-*.json`·`verdict.json`을 다시 쓰며 `source` 경로 접두어(옛 `out/evolution/candidates/…`)와 일부 딕셔너리 순서가 달라지므로, 이 폴더의 세 파일은 재실행 결과가 아니라 **원래 기록 그대로** 두었다(코드는 `source`의 파일명만으로 `candidates/`에서 소스를 찾는다).
